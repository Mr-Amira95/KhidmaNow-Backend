Payments API

Cash confirmation · CliQ confirmation · Card via Stripe
KhidmaNow Backend
v1 · 2026‑07‑28
GET — read POST — create PATCH — state change pending paid failed

One checkout endpoint creates a Payment row in every case, always starting pending. What confirms it into paid (or knocks it back to failed) differs by method — that's the whole shape of this change.

Removed: POST /v1/payments/{payment}/confirm — customers could previously mark their own payment as paid. That's gone; a customer can no longer self-confirm any method. Stop calling this endpoint.
01

Cash

Confirmed by the service provider
Customer checks out with cash→ Provider collects cash in person→ Provider confirms or rejects in-app
POST /v1/service-requests/{serviceRequest}/checkout customer · Bearer token

Same checkout endpoint used for all three methods — see the shared reference at the bottom for the full request/response shape.

PATCH /v1/provider/payments/{payment}/confirm provider · Bearer token

Marks the cash payment as received. No request body. Only works while the payment is pending, method is cash, and the payment belongs to this provider's service request.

PATCH /v1/provider/payments/{payment}/reject provider · Bearer token

Provider says the cash never arrived.

FieldTypeNotes
rejection_reasonstringrequired, max 1000 chars

On reject, status → failed and the customer is notified with the reason. payment_status on the service request stays unpaid, so the customer can call checkout again with any method.

02

CliQ

Confirmed by an admin
Customer views company CliQ alias→ Sends transfer, checks out with a receipt photo→ Admin reviews and confirms or rejects
GET /v1/company-cliq-details any authenticated user

Unchanged, already live. Call this before checkout to show the customer where to send the transfer.

{ "alias": "khidmanow@cliq", "bank_name": "Arab Bank", "holder_name": "KhidmaNow LLC" }
POST /v1/service-requests/{serviceRequest}/checkout customer · Bearer token

multipart/form-data for this method — a receipt image is required. See shared reference below.

PATCH /v1/admin/payments/{payment}/confirm admin · permission payments.edit

No body. Only works for cliq payments still pending. Admin should open GET /v1/admin/payments/{payment} first to view receipt_url before confirming.

PATCH /v1/admin/payments/{payment}/reject admin · permission payments.edit
FieldTypeNotes
rejection_reasonstringrequired, max 1000 chars
03

Card

Confirmed by Stripe, automatically
Customer checks out with card→ App confirms the PaymentIntent with Stripe SDK→ Stripe webhook flips status server-side
POST /v1/service-requests/{serviceRequest}/checkout customer · Bearer token

Response includes stripe_client_secret — pass it straight into Stripe's mobile SDK (PaymentSheet on iOS/Android, or the Flutter/RN equivalent) to collect the card and confirm the charge. The app never touches raw card numbers or talks to our backend again for this step.

This is the one flow with a real third party in the loop. Nothing in the mobile app calls a "confirm" endpoint for card — Stripe confirms client-side, then our server learns about it from a webhook (below), independent of the app being open.
POST /v1/webhooks/stripe Stripe only — not for the app

Listens for payment_intent.succeeded and payment_intent.payment_failed. Flips Payment.status to paid or failed and pushes a notification to the customer. Listed here only so the mobile team knows status changes can arrive without any request from the app.

Polling & push

For all three methods, GET /v1/service-requests/{serviceRequest} returns the latest payment attempt under data.payment — poll data.payment.status, or just listen for the push notification (type: "payment", type_id = payment id) that fires the moment it changes.

pending → paid or failed — on failed, the request stays payment_status: unpaid, so checkout can be called again.
Endpoints not listed here (payment index/show for admin, wallet, payouts) are unchanged by this work.
